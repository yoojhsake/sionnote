하이브리드 조인을 설정한 PC에서 Automatic-Device-Join을 실행했더니 `dsregcmd /status`에 Error Phase가 join, Client ErrorCode가 0x801c03f3, Server ErrorSubCode가 error_missing_device로 나왔습니다. SCP와 등록 서비스 탐색은 성공했고 컴퓨터 계정이 Entra에 아직 없어서 생긴 오류였으며, 계정이 올라온 뒤 같은 작업을 다시 실행하자 성공했습니다.

## 요약

- 탐색(discover)은 성공하고 조인(join) 단계에서 error_missing_device가 나면 장치 동기화 전 상태임
- Connect Sync는 Delta 동기화, Cloud Sync는 요청 시 프로비전으로 올린 뒤 같은 작업을 재실행하면 됨
- SCP를 다시 만들거나 PC를 도메인에서 빼지 않아도 됨

> 근거 표기: 조회 = 이 랩에서 직접 읽은 값 · 문서 = Microsoft Learn · 확인 불가 = 시도했지만 확인하지 못한 값(방법·사유 병기) · 추정 = 조회·문서로 직접 확인하지 못하고 관찰값에서 이어 붙인 해석. 테넌트 ID·테넌트 도메인·클라우드 계정(UPN)은 가렸고, 개인 실습용 도메인(sionnote.local)의 계정 이름·장치 이름·호스트 이름은 그대로 보일 수 있습니다.

## 전체 기록

### 1. 증상

도메인에 가입된 Windows 10 PC(cl10)에서 이 증상을 직접 읽었습니다(2026-11-03). 하루 뒤인 2026-11-04에는 도메인에 새로 가입시킨 Windows 11 PC(cl11)에서 같은 증상을 다시 만들어 고해상도로 캡처했습니다(아래 "Windows 11(cl11)에서 다시 확인"). 작업 스케줄러의 Automatic-Device-Join을 수동 실행한 뒤 결과를 읽었습니다.

- Windows 10 PC(cl10)에서 `LastTaskResult`가 1이었고 `AzureAdJoined`는 NO, `DomainJoined`는 YES(조회)
- `dsregcmd /status`에 Error Phase = join, Client ErrorCode = 0x801c03f3, Server ErrorCode = invalid_request, Server ErrorSubCode = error_missing_device가 표시됨(조회)
- 이벤트 뷰어의 User Device Registration/Admin 로그에 오류 이벤트 204와 304가 기록됨(조회)

**사용한 명령과 출력** — 조인 작업을 수동 실행한 뒤 결과를 읽은 PowerShell 화면입니다(화면에서 옮겨 적음, cl10, 2026-11-03).

```powershell
$p = '\Microsoft\Windows\Workplace Join\'
Start-ScheduledTask -TaskPath $p -TaskName 'Automatic-Device-Join'
Start-Sleep 40
Get-ScheduledTaskInfo -TaskPath $p -TaskName 'Automatic-Device-Join' | fl LastRunTime,LastTaskResult
dsregcmd /status      # 오류 항목만 발췌
```

```text
LastRunTime    : 2026-11-03 오후 3:46:46
LastTaskResult : 1

         AzureAdJoined : NO
          DomainJoined : YES
            AzureAdPrt : NO
   AzureAdPrtAuthority : NO
Diagnostics Reference  : www.microsoft.com/aadjerrors
            Error Phase : join
        Client ErrorCode : 0x801c03f3
        Server ErrorCode : invalid_request
     Server ErrorSubCode : error_missing_device
For more information, please visit https://www.microsoft.com/aadjerrors
```

`LastRunTime`(3:46:46)은 이벤트 화면의 시각(3:46:29~3:46:39)보다 몇 초 늦습니다. `LastRunTime`이 이벤트보다 늦은 것은 이 화면이 다른 실행의 값일 가능성이 높다는 신호입니다(추정). 두 값이 같은 실행의 것인지는 확인 불가입니다. 시도한 방법은 두 가지입니다. 하나는 작업 정보와 이벤트의 시각을 비교한 것인데, 실행 ID가 두 화면에 함께 나오지 않았습니다. 다른 하나는 작업 스케줄러의 실행 기록으로 그 시각의 시작·종료 이벤트를 찾는 것이었습니다. 2026-11-04에 cl10에서 다시 확인하니 작업 스케줄러 Operational 로그가 꺼져 있었고(`IsEnabled = False`) 11-03 15:40~16:00의 이벤트는 0건이었습니다(조회). 꺼져 있던 로그는 지난 실행을 나중에 만들어 낼 수 없어서 여기서 막힙니다.

```powershell
'TS-Operational enabled = ' + (Get-WinEvent -ListLog 'Microsoft-Windows-TaskScheduler/Operational').IsEnabled
$e = Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-TaskScheduler/Operational'; StartTime=[datetime]'2026-11-03 15:40'; EndTime=[datetime]'2026-11-03 16:00'} -ErrorAction SilentlyContinue
'TS events 11-03 15:40-16:00 = ' + @($e).Count
```

### 2. 원인 및 분석

공식 문서는 진단이 모두 통과하고도 디렉터리 오류로 등록이 실패하는 것이 sync-join에서는 예상된 동작이고, Entra Connect 동기화 작업이 끝나면 장치가 조인할 수 있다고 설명합니다(문서). 기대값은 동기화가 컴퓨터 계정을 Entra에 올려 둔 상태이고, 실제로는 올라오기 전이었습니다. 문서의 'Sync-join server errors' 표에는 메시지 'The device object by the given ID isn't found'가 sync-join에서 예상되는 오류로 있고, 이 글의 이벤트 204 메시지와 문구가 같습니다. 다만 문서는 이 메시지를 서버 오류 코드 DirectoryError로 적었고 이 글에서 본 것은 클라이언트 0x801c03f3, 서버 invalid_request/error_missing_device여서 코드는 일치하지 않습니다. 같은 상황으로 묶은 것은 이벤트 순서와 동기화 이후 성공한 결과에 근거한 판단입니다(추정).

#### 이벤트 로그에서 본 것

탐색 이벤트에는 "탐색 작업이 성공했습니다"가 있었고, 서버 응답에 등록 서비스(enterpriseregistration) 주소가 들어 있었습니다(조회). 그 뒤 약 1초 안에 오류 이벤트가 이어졌습니다.

**GUI 확인 경로**: cl10에서 이벤트 뷰어(`eventvwr`) → 응용 프로그램 및 서비스 로그 → Microsoft → Windows → **User Device Registration** → **Admin**을 엽니다. 이 로그를 "이벤트 ID" 열로 정렬하면 같은 번호끼리 모입니다(조회, cl10, 2026-11-04).

오류(빨간 아이콘)는 11월 3일 오후에 204가 1건(3:46:39), 304가 3건(3:28:49, 3:30:09, 3:46:39)으로 보입니다. 같은 그림 아래쪽에는 오류 307도 3:28:49와 3:30:09에 보이는데, 이 이벤트는 열어 보지 않았습니다(조회). 위 캡처에는 정렬된 목록의 일부 구간만 보입니다. 204를 열면 일반 탭에 가져오기 결합 응답 작업이 코드 0x801c03f3으로 실패했고, 서버 반환 HTTP 상태가 400이며, 서버 응답이 `invalid_request` / `error_missing_device`, 메시지가 "The device object by the given id (…) is not found.", operation이 `DeviceRenew`라고 나옵니다(조회). 아래 캡처는 메시지 앞부분까지만 잘려 있어 operation 줄은 화면에 없고, 이벤트 본문에서 읽은 값입니다. 장치 ID와 활동 ID는 가렸습니다.

더 이른 시각의 304(3:30:09)는 다른 코드입니다. 종료 코드 0x801c001d이고 테넌트 유형·테넌트 ID 같은 항목이 모두 undefined입니다(조회, 3:30:09 이벤트만 열어 봄. 3:28:49의 304는 열지 않음). 공식 문서는 이 코드를 `DSREG_AUTOJOIN_ADCONFIG_READ_FAILED`로, SCP 개체를 읽어 Entra 테넌트 정보를 얻지 못한 경우로 설명합니다(문서). 그래서 3:30:09의 304는 SCP를 읽지 못하던 시점의 실패로 보이고(3:28:49의 304와 307은 열지 않아, 같은 유형이라는 것은 시각이 가깝다는 점에 근거한 추정), SCP를 읽은 뒤에는 0x801c03f3으로 바뀌었다고 추정합니다(추정: 시각 순서와 문서 설명의 일치, SCP 생성 시각은 이번에 확인하지 않음).

```powershell
Get-WinEvent -LogName 'Microsoft-Windows-User Device Registration/Admin' -MaxEvents 10 | ft TimeCreated,Id,LevelDisplayName -Auto
```

#### AD 쪽 상태

컴퓨터 계정에는 userCertificate 값이 1개 기록되어 있었고, SCP도 읽혔습니다(조회). 즉 PC가 자기 인증서를 올리는 단계까지는 끝나 있었습니다.

```powershell
$c = ([adsisearcher]'(&(objectClass=computer)(name=sionnote-cl10))').FindOne()
'userCertificate count: ' + $c.Properties.usercertificate.Count
[ADSI]::Exists('LDAP://CN=62a0ff2e-97b9-4513-943f-0d221bd30080,CN=Device Registration Configuration,CN=Services,CN=Configuration,DC=sionnote,DC=local')
```

#### 재시도

- Connect Sync 경로: sync01에서 `Start-ADSyncSyncCycle -PolicyType Delta`를 실행한 뒤 같은 작업을 다시 실행해 LastTaskResult 0, AzureAdJoined YES가 됐습니다(조회).
- Cloud Sync 경로(2026-11-03): 요청 시 프로비전으로 컴퓨터를 올리자 장치 목록에 "보류 중"으로 나타났고, 작업을 다시 실행해 성공했습니다(조회).

### 3. 결론

PC가 SCP로 등록 서비스를 찾고 인증서를 AD에 기록함 → 컴퓨터 계정이 아직 Entra에 동기화되지 않음 → 서버가 장치를 찾지 못해 error_missing_device → 동기화 뒤 재시도에서 성공.

cl11의 11월 4일 재현에서는 Entra 감사 로그에 21:48:46 장치 Unregister/Delete가 있고(이 삭제를 일으킨 조작은 기록하지 않았습니다. 도메인을 떠나면 PC가 스스로 레코드를 지우는 [Entra 조인 글]({{ "/iam/entra-join-cl10-cl11/" | relative_url }})의 사례와 같은 유형의 기록으로 보입니다, 추정) 21:54:59에 Restore가 이어집니다(조회). 가입 직후 오류가 난 시점에 장치 레코드가 없었다는 점은 error_missing_device와 맞지만, 오류를 읽은 정확한 시각은 기록하지 않아 둘의 선후는 이어 붙이지 않았습니다.

같은 하이브리드 조인 실패라도 레코드가 이미 있는 PC(cl10)에서는 다른 코드가 나왔습니다. 0x801c005b(error_computer_signature_check_failure)이며, 사례와 해결은 [Connect Sync 글]({{ "/iam/hybrid-join-connect-sync/" | relative_url }})에 정리했습니다.

확인 불가가 하나 있습니다. 0x801c03f3 코드 자체의 이름과 의미는 이번에 찾은 문서에서 확인하지 못했고(방법: Learn 검색을 세 차례 했고, 사유: 하이브리드 조인 문제 해결 문서의 오류 코드 표에 0x801c03f3은 없음. 바로 앞 번호 0x801c03f2는 `DSREG_E_DIRECTORY_FAILURE`, 즉 DRS가 DirectoryError를 돌려준 경우로 표에 있어 같은 계열로 보이지만 03f3 자체의 설명은 아님), error_missing_device 문구와 재시도 결과로 위 원인을 판단했습니다.

### 4. 권고방안

1. 컴퓨터 계정이 동기화 범위(OU)에 있고 userCertificate 값이 있는지 확인합니다. Connect Sync는 Delta 동기화를 수동으로 실행하고, Cloud Sync는 요청 시 프로비전의 디바이스 탭에 컴퓨터의 고유 이름(DN)을 넣습니다.
2. 장치 목록(Entra ID → 장치 → 모든 디바이스)에서 등록됨 열이 "보류 중"이면 올라온 것입니다. 이어서 Automatic-Device-Join을 다시 실행하고 LastTaskResult가 0인지 확인합니다.
3. SCP를 다시 만들거나 PC를 도메인에서 빼지 마세요. 탐색 단계가 이미 성공했다면 SCP는 정상입니다.
