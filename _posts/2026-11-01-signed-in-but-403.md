로그인은 분명히 성공했는데 화면에는 "권한이 없습니다", Graph는 403, Azure는 `AuthorizationFailed`가 나옵니다. 인증은 통과했고 권한 부여에서 막힌 것이라, 역할과 범위 확인부터 PIM 활성화, 토큰 갱신까지 순서대로 보면 됩니다.

## 요약

- 403은 권한 부여에서 막힌 것이라 권한이 없으면 다시 로그인해도 그대로임
- Entra 역할인지 Azure 역할인지 가른 뒤 범위와 PIM 활성화 여부를 확인함
- 역할을 할당해도 반영까지 최대 10분이 걸리고 다시 로그인해야 함

> Microsoft Learn 문서(2026-11-01 확인) 기준입니다. Azure 역할 없음, PIM 적격만 있음, 읽기 권한자로 쓰기 시도, Entra 역할 없음의 네 경우는 샌드박스 테넌트에서 시험 사용자로 직접 재현했습니다. 게스트, 앱 API 권한, Graph 라이선스 경우는 문서 기준입니다. 함께 볼 글: [Entra ID 핵심 개념: 기초와 구조 편]({{ "/iam/what-is-entra-id/" | relative_url }}), [오류 코드 읽는 법]({{ "/iam/entra-id-error-codes/" | relative_url }}).

## 전체 내용

### 1. 증상

- Entra 관리 센터: 사용자 속성 저장 버튼이 비활성이거나 "권한이 없습니다"
- Azure 포털 VM 생성: `The client ... does not have authorization to perform action ... over scope ... (code: AuthorizationFailed)`
- Graph·REST 호출: `403 Forbidden`과 `Authorization_RequestDenied`("Insufficient privileges to complete the operation.")

### 2. 원인 및 분석

403은 토큰은 유효하나 권한이 없다는 뜻입니다([Microsoft Graph error responses](https://learn.microsoft.com/graph/errors)). 함께 오는 **서비스 오류 코드**(Graph `Authorization_RequestDenied`, Azure `AuthorizationFailed`, `insufficient_claims`)로 좁힙니다.

<details markdown="1">
<summary>서비스 오류 코드, HTTP 상태 코드 비교, 권한 종류별 확인 위치 보기</summary>

- **Authorization_RequestDenied**(Graph): 앱 권한(스코프)이나 Entra 역할이 모자람
- **AuthorizationFailed**(Azure): 메시지에 나온 범위(scope)에서 그 작업(action)을 할 Azure 역할이 없음
- **insufficient_claims**(Graph, 조건부 액세스 리소스): 권한이 아니라 MFA 같은 추가 조건을 채워 다시 로그인하라는 뜻
- Graph에서는 필요한 **라이선스가 없을 때**도 403이 나올 수 있음(문서)

서버는 요청 결과마다 세 자리 **HTTP 상태 코드**를 돌려줍니다. 2xx는 성공, 4xx는 요청 쪽(사용자·앱·설정) 문제, 5xx는 서비스 쪽 문제입니다. 상태 코드 전체와 AADSTS 번호 읽는 법은 [오류 코드 읽는 법]({{ "/iam/entra-id-error-codes/" | relative_url }})에 정리했습니다.

- **401 Unauthorized**: 출입증(토큰)이 없거나 만료됨 → 다시 로그인하면 대부분 해결
- **403 Forbidden**: 출입증은 유효한데 그 방에 들어갈 권한이 없음 → 다시 로그인해도 권한이 없으면 그대로
- **404 Not Found**: 대상이 없음 → ID·이름·테넌트 확인
- **429 Too Many Requests**: 요청이 너무 많아 잠시 막힘 → Retry-After만큼 기다렸다 재시도

#### 어떤 종류의 권한인가

- **사용자, 그룹, 앱, 조건부 액세스 관리**
    - 필요한 권한 종류: Entra 역할(예: 사용자 관리자, 조건부 액세스 관리자)
    - 확인 위치(GUI): Entra 관리 센터 > 사용자 > 해당 사용자 > Assigned roles(할당된 역할)
- **구독, 리소스 그룹, VM, 스토리지 관리**
    - 필요한 권한 종류: Azure RBAC 역할(예: Virtual Machine Contributor)
    - 확인 위치(GUI): Azure 포털 > 해당 범위 > Access control (IAM) > Role assignments
- **앱이 Graph API 호출**
    - 필요한 권한 종류: API 권한(스코프) + 관리자 동의
    - 확인 위치(GUI): 앱 등록 > API permissions

</details>

<details markdown="1">
<summary>원인별 확인과 대처 자세히 보기</summary>

- **역할이 없음**
    - 확인: 위 '어떤 종류의 권한인가'에 적은 확인 위치의 역할 목록
    - 대처: 작업에 필요한 **최소 권한** 역할을 할당
- **범위가 다름**
    - 확인: 리소스 그룹 A에 역할이 있는데 리소스 그룹 B에서 작업
    - 대처: 작업할 범위(또는 상위 범위)에 할당. 관리 단위(AU) 범위 Entra 역할도 같은 원리
- **방금 할당해서 반영 전**
    - 확인: 할당 시각 확인
    - 대처: Azure RBAC는 반영까지 **최대 10분**(문서). 포털, PowerShell, CLI는 **로그아웃 후 다시 로그인**하면 갱신됨
    - REST는 액세스 토큰을 새로 받기
- **PIM 적격만 있음**
    - 확인: My roles(내 역할)에서 "적격(Eligible)"으로만 보임
    - 대처: PIM에서 **활성화**한 뒤 다시 시도. 활성화 직후에도 토큰 갱신이 필요할 수 있음
- **게스트 사용자**
    - 확인: 게스트 계정으로 접근
    - 대처: 게스트도 해당 범위에 역할 할당이 있어야 함
- **앱의 API 권한 부족(Authorization_RequestDenied)**
    - 확인: 앱 등록의 API permissions, 동의 여부. Graph PowerShell은 `Find-MgGraphCommand`로 필요한 권한 확인
    - 대처: 필요한 권한 추가 후 관리자 동의. 이미 받은 토큰은 새로 발급받아야 반영됨
- **라이선스 없음(Graph)**
    - 확인: 사용자에게 해당 서비스 라이선스가 있는지
    - 대처: 라이선스 할당 후 다시 시도

</details>

샌드박스에서 역할이 없는 시험 사용자로 재현한 결과는 아래와 같습니다(화면은 4절 아래 "샌드박스에서 직접 한 화면 보기").

- **Azure 역할 없음**: 리소스 그룹 만들기의 구독 목록이 비어 있고, 구독 주소로 바로 들어가면 "액세스 권한 없음"(포털 오류 코드 401)이 뜸. 403 문구가 아니라 **구독이 안 보이는** 형태로 나타남
- **PIM 적격만 있음**: 구독 범위 읽기 권한자(포털 표시 이름 "독자")를 적격으로 할당했지만, 활성화 전에는 역할이 없을 때와 똑같이 구독 목록이 비어 있음
- **PIM 활성화 뒤**: 포털을 새로 고치자 구독이 보임. 리소스 그룹 만들기는 포털이 "구독에서는 리소스 그룹을 만들 수 있는 권한이 없습니다"로 미리 막았고, Cloud Shell의 `az group create`는 `AuthorizationFailed`(action `Microsoft.Resources/subscriptions/resourcegroups/write`)를 돌려줌. 같은 계정으로 `az group list`(읽기)는 성공함
- **Entra 역할 없음**: 다른 사용자의 개요 화면에서 속성 편집, 삭제, 세션 취소 버튼이 비활성으로 표시됨

### 3. 결론

`역할 없음·범위 다름·PIM 미활성·반영 전 토큰 → 권한 부여 실패 → 403, AuthorizationFailed`

재로그인만으로는 안 풀리고, 역할·범위를 고친 뒤 토큰을 갱신해야 합니다. 역할이 전혀 없거나 적격만 있을 때는 403 문구보다 **구독이 아예 보이지 않는** 모습으로 먼저 나타납니다(샌드박스 재현).

### 4. 권고방안

1. 조치: 작업 범위에 **최소 권한** 역할을 할당하고, PIM 적격이면 활성화한 뒤 다시 로그인(REST는 토큰 재발급)합니다.
2. 조치 후 확인: Azure는 범위의 Access control (IAM) > Check access에서 실제 적용 역할을, Entra는 사용자 > Assigned roles의 활성 역할과 감사 로그(Monitoring & health > Audit logs)의 할당 기록을 봅니다.
3. 예방: 상시 권한 대신 **PIM 적격 할당**과 "작업 전 활성화 → 반영 대기 → 재로그인" 교육. 역할은 그룹에 할당하고 범위는 필요한 만큼만.
