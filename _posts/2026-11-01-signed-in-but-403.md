로그인은 분명히 성공했는데 화면에는 "권한이 없습니다", Graph는 403, Azure는 `AuthorizationFailed`가 나옵니다. 인증은 통과했고 권한 부여에서 막힌 것이라, 역할과 범위 확인부터 PIM 활성화, 토큰 갱신까지 순서대로 보면 됩니다.

## 요약

- 로그인은 성공. 그런데 화면에 "권한이 없습니다", Graph는 `403 Forbidden`(`Authorization_RequestDenied`), Azure는 `AuthorizationFailed`
- 인증(누구인가)은 통과했고 권한 부여(무엇을 할 수 있나)에서 막힘. 로그인 오류(AADSTS)와는 보는 곳이 다름
- 필요한 권한이 Entra 역할(사용자·그룹·정책 관리)인지, Azure RBAC 역할(구독·리소스 그룹·리소스)인지부터 구분
- 흔한 원인은 역할이 없음, 범위(scope)가 다름, 방금 할당해서 아직 반영 안 됨, PIM 적격만 있고 활성화 안 함, 토큰이 옛 권한을 담고 있음
- 역할·범위 확인 → PIM 활성화 → 최대 10분 대기 → 로그아웃 후 다시 로그인(토큰 갱신)

> Microsoft Learn 공식 문서(2026-11-01 확인)를 기준으로 쓴 대처 가이드입니다. 특정 테넌트에서 재현한 기록은 아닙니다. 개념은 [Entra ID 핵심 개념: 기초와 구조 편]({{ "/iam/what-is-entra-id/" | relative_url }})을 함께 보세요. 오류 번호와 HTTP 상태 코드가 낯설면 [오류 코드 읽는 법]({{ "/iam/entra-id-error-codes/" | relative_url }})을 먼저 보세요.

## 전체 내용

### 1. HTTP 상태 코드로 본 403

서버는 요청 결과마다 세 자리 **HTTP 상태 코드**를 돌려줍니다. 2xx는 성공, 4xx는 요청 쪽(사용자·앱·설정) 문제, 5xx는 서비스 쪽 문제입니다. 이 글의 403은 4xx 묶음입니다.

- **401 Unauthorized**: 출입증(토큰)이 없거나 만료됨 → 다시 로그인하면 대부분 해결
- **403 Forbidden**: 출입증은 유효한데 그 방에 들어갈 권한이 없음 → 다시 로그인해도 권한이 없으면 그대로
- **404 Not Found**: 대상이 없음 → ID·이름·테넌트 확인
- **429 Too Many Requests**: 요청이 너무 많아 잠시 막힘 → Retry-After만큼 기다렸다 재시도

403과 함께 오는 **서비스 오류 코드**가 원인을 더 좁혀 줍니다.

- **Authorization_RequestDenied**(Graph): 앱 권한(스코프)이나 Entra 역할이 모자람
- **AuthorizationFailed**(Azure): 메시지에 나온 범위(scope)에서 그 작업(action)을 할 Azure 역할이 없음
- **insufficient_claims**(Graph, 조건부 액세스가 걸린 리소스): 권한이 아니라 MFA 같은 추가 조건을 채워 다시 로그인하라는 뜻
- Graph에서는 필요한 **라이선스가 없을 때**도 403이 나올 수 있음(문서)

상태 코드 전체와 AADSTS 번호 읽는 법은 [오류 코드 읽는 법]({{ "/iam/entra-id-error-codes/" | relative_url }})에 정리했습니다.

### 2. 증상

- Entra 관리 센터에서 사용자 속성을 고치려는데 저장 버튼이 비활성이거나 "권한이 없습니다"가 나옵니다.
- Azure 포털에서 VM을 만들려는데 `The client ... does not have authorization to perform action ... over scope ... (code: AuthorizationFailed)`가 나옵니다.
- Graph나 REST 호출이 `403 Forbidden`과 `Authorization_RequestDenied`("Insufficient privileges to complete the operation.")를 돌려줍니다.

### 3. 원인과 해결

인증은 통과했고 권한 부여에서 막힌 것입니다. 필요한 권한이 Entra 역할인지 Azure RBAC 역할인지(아래 '어떤 종류의 권한인가') 먼저 가른 뒤 원인별로 대처합니다.

- **역할이 없음**
    - 확인: 아래 '어떤 종류의 권한인가'에 적은 확인 위치의 역할 목록
    - 대처: 작업에 필요한 **최소 권한** 역할을 할당
- **범위가 다름**
    - 확인: 리소스 그룹 A에 역할이 있는데 리소스 그룹 B에서 작업
    - 대처: 작업할 범위(또는 상위 범위)에 할당. 관리 단위(AU) 범위 Entra 역할도 같은 원리
- **방금 할당해서 반영 전**
    - 확인: 할당 시각 확인
    - 대처: Azure RBAC는 반영까지 **최대 10분**(문서). 포털, PowerShell, CLI는 **로그아웃 후 다시 로그인**하면 갱신됨
    - REST는 액세스 토큰을 새로 받기
- **PIM 적격만 있음**
    - 확인: My roles(내 역할)에서 "적격(Eligible)"으로만 보임
    - 대처: PIM에서 **활성화**한 뒤 다시 시도. 활성화 직후에도 토큰 갱신이 필요할 수 있음
- **게스트 사용자**
    - 확인: 게스트 계정으로 접근
    - 대처: 게스트도 해당 범위에 역할 할당이 있어야 함
- **앱의 API 권한 부족(Authorization_RequestDenied)**
    - 확인: 앱 등록의 API permissions, 동의 여부. Graph PowerShell은 `Find-MgGraphCommand`로 필요한 권한 확인
    - 대처: 필요한 권한 추가 후 관리자 동의. 이미 받은 토큰은 새로 발급받아야 반영됨
- **라이선스 없음(Graph)**
    - 확인: 사용자에게 해당 서비스 라이선스가 있는지
    - 대처: 라이선스 할당 후 다시 시도

#### 신입 운영자가 리소스 그룹에서 VM을 못 만든 경우

팀장이 운영자에게 구독의 **Reader**와 리소스 그룹 `rg-dev`의 Virtual Machine Contributor를 할당했습니다. 운영자가 바로 `rg-prod`에서 VM을 만들자 AuthorizationFailed가 납니다.

역할 자체는 있지만 **범위가 rg-dev**이기 때문입니다. `rg-dev`에서 다시 시도하자 이번엔 할당 직후라 같은 오류가 나고, 로그아웃 후 다시 로그인하자 성공합니다. 범위 문제와 반영 지연이 한 번에 겹친 경우입니다.

### 4. 같은 문의를 줄이려면

상시 권한 대신 **PIM 적격 할당**을 쓰되, 운영자에게 "작업 전 활성화 → 반영 대기 → 재로그인" 순서를 교육합니다. 역할은 사람이 아니라 그룹에 할당하고, 범위는 필요한 만큼만 좁힙니다.

### 5. 확인 과정

<details markdown="1">
<summary>확인 과정 자세히 보기</summary>

#### 어떤 종류의 권한인가

- **사용자, 그룹, 앱, 조건부 액세스 관리**
    - 필요한 권한 종류: Entra 역할(예: 사용자 관리자, 조건부 액세스 관리자)
    - 확인 위치(GUI): Entra 관리 센터 > 사용자 > 해당 사용자 > Assigned roles(할당된 역할)
- **구독, 리소스 그룹, VM, 스토리지 관리**
    - 필요한 권한 종류: Azure RBAC 역할(예: Virtual Machine Contributor)
    - 확인 위치(GUI): Azure 포털 > 해당 범위 > Access control (IAM) > Role assignments
- **앱이 Graph API 호출**
    - 필요한 권한 종류: API 권한(스코프) + 관리자 동의
    - 확인 위치(GUI): 앱 등록 > API permissions

**Entra 역할과 Azure RBAC는 별개**입니다. 전역 관리자라도 기본적으로 Azure 구독의 리소스를 관리할 권한은 없습니다.

#### 해결 확인

Azure는 해당 범위의 Access control (IAM) > Check access에서 사용자를 검색해 실제 적용되는 역할을 확인합니다. Entra는 사용자 > Assigned roles에서 활성 역할을 확인하고, 감사 로그(Monitoring & health > Audit logs)에서 역할 할당 기록을 봅니다.

</details>
